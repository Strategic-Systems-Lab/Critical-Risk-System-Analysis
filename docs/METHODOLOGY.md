# Methodology & Limitations

This document explains how RiskAI calculates its results, what assumptions those calculations rest on, and — just as importantly — what the platform does not and cannot do.

---

## Methodology

### Risk Scoring

Each risk category is calculated by a shared formula that compares a **"bad" factor** (inputs that increase risk) against a **"good" factor** (inputs that offset it), scaled by:

- a **sensitivity multiplier** specific to that category (how sharply it reacts to input changes)
- the **simulation horizon** (risk compounds slightly with more years)
- a **domain-specific floor and ceiling** (each category has a realistic minimum and maximum it can reach)

The result is deterministic: identical inputs always produce identical outputs. There is no randomness in the risk calculation itself.

### Stability Score

A single stability score per simulation is derived by aggregating a subset of "good" and "bad" factors relevant to that domain, weighted against a domain-specific baseline. The multi-year trajectory shown in the sparkline chart uses a deterministic curve toward that stability value — not a stochastic (random-walk) projection.

### Current Model Type

RiskAI's risk models are **rule-based**, not machine-learning-based. Every formula is a fixed, human-authored expression — there is no training data, no learned parameters, and no model that updates itself over time. Formulas are calibrated by domain reasoning and stress-testing against edge cases, not by fitting to historical outcomes.

### AI-Style Reporting

The "Strategic Analysis Engine" report is generated by a template-driven text engine that reads the calculated risk values and assembles a structured narrative (situation assessment, root cause explanation, priority actions, trajectory forecast). It is not a live large language model call — the app is explicit about this in its own UI.

### Architecture for Future Models

Package 1 (the core simulation engine) and Package 2 (the Risk Intelligence layer) are deliberately decoupled: Package 2 only ever reads a finished simulation result and never touches Package 1's calculations. This means a future, more sophisticated risk model (see [Future Improvements](#future-improvements)) could replace or extend Package 1's formulas without requiring changes to Package 2, the UI, or the reporting layer.

## Explainability

RiskAI is built on the position that a risk score without a visible cause is close to useless for decision-making.

Every generated recommendation in Package 2's Mission Engine is tied back to the specific input parameter(s) that drive the underlying risk category — not a generic "improve this" statement. A user working on Retirement risk, for example, sees exactly which levers (`pension_assets`, `state_pension_reliance`) are responsible for a given score, rather than a category name alone.

This matters more than raw predictive accuracy for a tool positioned as decision support rather than a forecast: a user needs to know **why** a number moved and **what to change**, not just that it moved. Transparent, traceable formulas make that possible in a way opaque scoring cannot.

## Assumptions

RiskAI's outputs rest on several explicit assumptions:

- **User input accuracy** – results are only as meaningful as the values a user provides; no input validation against external data sources occurs
- **Simplified models** – each domain uses a small number of representative risk factors (up to 10), not an exhaustive real-world risk taxonomy
- **Scenario-based estimation** – outputs represent a plausible trajectory given the stated inputs, not a statistical forecast with confidence intervals
- **Domain-specific calibration** – risk percentages are not directly comparable across domains (a 60% Cyber risk for a Company and a 60% Vacancy risk for Real Estate are calibrated independently, not on a shared scale)

---

## Limitations

RiskAI is a **demonstration and research-oriented project**, and its outputs should be read accordingly:

- **Not financial advice** – wealth and net-worth projections are illustrative, not investment recommendations
- **Not medical advice** – Healthcare domain results do not constitute clinical or public-health guidance
- **Not legal advice** – no output should be relied on for compliance or legal decisions
- **No guarantee of predictive accuracy** – formulas are directionally reasoned, not empirically validated against real-world outcome data
- **Decision support, not decision-making** – outputs are a starting point for discussion and further analysis, not a substitute for professional judgment

---

## Future Improvements

Planned or plausible directions for the modeling layer:

- **Machine learning models** – replacing or supplementing rule-based formulas with models trained on real outcome data, where such data becomes available
- **Monte Carlo simulation** – probabilistic trajectories with confidence intervals instead of a single deterministic path
- **Bayesian networks** – explicit modeling of dependencies between risk categories, beyond the current correlation heuristics
- **Real-time economic / market data** – calibrating domain parameters (e.g., interest rates, regional real estate indices) against live external sources
- **API integrations** – connecting to authoritative third-party data providers per domain
- **Custom risk models** – allowing organizations to supply their own weighting or formulas per domain

None of these are implemented today. This section describes direction, not a roadmap with committed timelines.
